# `db/`

Schema and seed data. The operational reference; the reasoning behind the
choices is in the migration's own header and in
[ADR 0009](../docs/adr/0009-runtime-registries-in-process.md).

```
db/
├── migrations/   golang-migrate, numbered up/down pairs
└── seeds/        dev fixtures, applied only by docker compose
```

## Migrations

Applied by the `migrate` service in the dev stack, and directly by the Go test
harness (`tests/integration/internal/harness/migrate.go`).

```
000001_initial_schema.up.sql      roles, users, user_roles, products,
000001_initial_schema.down.sql    containers, container_items, telemetry_logs
```

One migration, seven tables. There used to be a second — `permissions`,
`marker_groups` and `markers`, in `ENGINE=MEMORY`, with an hourly purge `EVENT`.
Those existed because the PHP runtime forked four workers that shared nothing but
the database. The API is one process now and the three registries live inside it;
see [ADR 0009](../docs/adr/0009-runtime-registries-in-process.md).

### Adding one

```
db/migrations/000002_<snake_case_name>.up.sql
db/migrations/000002_<snake_case_name>.down.sql
```

Rules, all of them load-bearing:

1. **Both files, always.** The test harness resets by dropping and
   re-migrating, so a missing or incorrect `down` breaks every integration test,
   not just the new one.
2. **The `down` must be a true inverse**, dropping in reverse
   foreign-key-dependency order.
3. **Every statement survives a second application** — `CREATE TABLE IF NOT
   EXISTS`, `DROP TABLE IF EXISTS`. `schema_migrations` already prevents a double
   apply on the normal path; this protects the operator who pipes a file straight
   into `mariadb` during an incident and would otherwise get "table already
   exists" and a half-applied file.
4. **A `search_*` column** alongside anything that will be filtered by `LIKE`,
   filled by the repository from `infra::text::search_key`. Filtering the display
   column directly makes the result depend on accents and case.

Run them:

```bash
docker compose up migrate                 # dev stack
dagger call integration-test               # harness does its own
```

## What the column types are, and why

The migration header says this at length; the short version, because getting one
of these wrong fails at *read* time rather than at migrate time:

| Kind | Type | Because |
|---|---|---|
| Entity id | `BIGINT` | A Snowflake is 63 bits and always positive. Every id is read as `i64`, and an `UNSIGNED` column would need a narrowing cast at the edge to get there. |
| Enum | `TINYINT` | Holds the **ordinal**, the same number `common.fbs` publishes. Signed, so it decodes; `CHECK` pins the range. |
| Timestamp | `BIGINT` | Epoch **milliseconds**, written by the application. A date type would make the stored instant depend on interpretation — `TIMESTAMP` converts twice and expires in 2038, `DATETIME` stores a zoneless wall clock. |
| Weight, capacity, density | `DOUBLE` | Matches the `f64` the domain computes with. These are measurements, not money. |
| `roles.permissions` | `JSON` | MariaDB implements it as `LONGTEXT` plus a validity `CHECK`, which is what lets the driver read it as text and parse it itself. |

**Ids are never `AUTO_INCREMENT`** — they are generated by the application. The
one exception is `telemetry_logs`, whose id *is* the order the entry was written
in.

## Timestamps and deletion

- A **strong** entity (`roles`, `users`, `products`, `containers`) carries
  `created_at`, `updated_at` and `deleted_at`, and is removed by soft-delete: the
  row stays and every read filters `deleted_at IS NULL`. The application never
  writes `created_at`/`updated_at`; the column defaults do.
- A **weak** entity (`container_items`) carries only `created_at` and is deleted
  for real. There is nothing to preserve in a row that existed only while a
  product sat in a container.
- An **association** (`user_roles`) carries neither, and has no lifecycle of its
  own. Replacing a user's roles is a `DELETE` followed by `INSERT`s.

### Uniqueness under soft-delete

`users.email` and `containers.code` are unique **among the living**. A plain
`UNIQUE` would keep an address reserved by someone removed years ago — and the
application, whose lookups filter deleted rows, would see it as free and then hit
a duplicate-key error it has no reason to expect.

MariaDB has no partial index, so a generated column carries the distinction: `0`
while the row lives, the row's own id once it does not.

```sql
live_key BIGINT AS (IF(deleted_at IS NULL, 0, id)) STORED,
UNIQUE KEY uq_users_email_live (email, live_key)
```

Living rows therefore collide with each other and with nothing else. Nothing
selects or writes `live_key`; every statement the application issues names its
columns explicitly, which is what keeps the column invisible to it.

## Seeds

`seeds/dev.sql`, applied only by the compose `seed` service, after migrations.
CI and the integration tests never load it — they build their data through
factories and `POST /setup`.

**It creates no user and no role.** Bootstrapping is the endpoint:

```bash
curl -X POST localhost:8000/setup -H 'Content-Type: application/json' \
     -d '{"name":"Admin","email":"admin@portmaster.local","password":"Portmaster1"}'
```

That is the path a real deployment uses, so the dev stack uses it too. Seeding a
user in SQL would mean carrying a pre-computed argon2id hash and a hand-copied
permission list — and that list had already drifted three slugs behind the code
before anyone noticed. See
[ADR 0004](../docs/adr/0004-setup-endpoint-instead-of-a-seeded-user.md).

**It must stay idempotent.** The `seed` service runs on every
`docker compose up`, and `db_data` survives anything short of `down -v`, so
re-seeding a populated database is the normal case. `app` waits on
`seed: service_completed_successfully` — a failing seed means the API never
starts at all.

Use `ON DUPLICATE KEY UPDATE`, not `INSERT IGNORE`: re-seeding should bring a row
back to the declared value, not silently accept whatever was left there.

```sql
INSERT INTO products (id, name, density, risk_class, search_name) VALUES
    (1, 'Liquid Nitrogen', 0.807, 1, 'liquid nitrogen')
ON DUPLICATE KEY UPDATE
    name = VALUES(name), density = VALUES(density),
    risk_class = VALUES(risk_class), search_name = VALUES(search_name);
```

Note the `1`: enum columns hold ordinals, and a typo there is caught by the
column's `CHECK` at seed time rather than surfacing as a failed read later.

Where a denormalised column is restored, the rows behind it must be written in
the same file — the seed rewrites `container_items` for the containers it
declares, or a container would claim 213 kg while holding nothing.

Verify by running it twice:

```bash
docker compose down && docker compose up -d    # note: no -v
docker compose ps seed                         # exited (0)
curl -fsS localhost:8000/info                  # app started
```
