§portmaster-app

Orquestração. Depende de domain (TableModules, traits de objeto) e de infra (repositories, escopo da tarefa, cache).

Dono dos Command DTOs, dos Query DTOs e dos traits de Service — que são exatamente os ports de que a apresentação precisa, e por isso são definidos aqui: o api-http conhece só esta camada.

Um service é o agrupamento; um caso de uso é o método dele, como um handler é o método do controller. RoleService::create é um caso de uso.

É aqui que a autorização acontece. Cada caso de uso protegido declara no construtor a permissão que exige e a confere na primeira linha, contra o UserContext que veio no Command — o contexto chega por argumento, nunca de um estado global. É também o único lugar que abre o escopo da tarefa: o MasterScope::run marca onde a unidade de trabalho começa e termina, e a camada não sabe o que a infra carrega dentro dele.

§O que esta camada reexporta, e por quê

O api-http conhece só o app. Então tudo que ele precisa e que nasce abaixo — o trait User para mapear ao fio, as Views de leitura, o Logger, os geradores de id — sai daqui. Não é conveniência: é o que mantém o grafo de dependências com uma seta só entre cada par de camadas.
