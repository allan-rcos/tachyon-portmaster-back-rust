O token de sessão — assunto exclusivo desta camada.

Nenhuma outra camada sabe o que é um JWT. O app devolve um usuário com os papéis dele; empacotar aquilo num token assinado, pôr num cookie e desfazer o caminho na requisição seguinte é trabalho daqui e de mais ninguém. Se um dia a sessão virar cookie de servidor, só este arquivo muda.

§O principal viaja como FlatBuffers dentro da claim

O JWT não carrega claims soltas por usuário. O principal inteiro — id, nome, e-mail, papéis e permissões — é serializado na tabela TokenUser de token.fbs, codificado em base64url e posto numa claim só. Duas razões: o token fica menor que o JSON equivalente, e o payload deixa de ser legível para quem espia o cookie por curiosidade.

Não é sigilo — base64 não esconde nada de quem queira ler. O que a assinatura garante é integridade: o conteúdo não pode ser alterado sem o segredo.

O refresh é outra coisa, e mora em RefreshToken.
