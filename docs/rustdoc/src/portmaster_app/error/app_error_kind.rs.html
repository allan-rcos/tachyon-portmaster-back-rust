1//! A natureza de uma falha comum, sem falar de transporte.
2
3/// De que tipo é a recusa que o [`AppError`] carrega.
4///
5/// Existe para que quem consome o erro comum não precise casar variante por
6/// variante só para decidir o que fazer com ele. O agrupamento é por **natureza
7/// da falha** — a validação do domínio é validação, venha ela de um usuário, de
8/// um papel ou de um manifesto — e deliberadamente **não** por intenção de
9/// protocolo: quem traduz isto para um status HTTP é a camada de API, e ela é a
10/// única que pode, porque é a única que sabe que existe HTTP.
11///
12/// A diferença importa quando aparecer uma segunda apresentação. Um CLI não tem
13/// 422; tem código de saída. Um consumidor de fila não tem 403; tem
14/// *dead letter*. Os dois conseguem decidir a partir daqui, e nenhum precisa
15/// desfazer uma tradução que o `app` já tivesse feito.
16///
17/// As recusas **próprias de um serviço** não passam por aqui: elas são poucas,
18/// específicas, e o controller que chamou aquele caso de uso as casa uma a uma —
19/// é o que faz `GET /products/{id}` responder 404 com o id que faltou em vez de
20/// um "ausência" genérico.
21///
22/// [`AppError`]: crate::error::AppError
23#[derive(Debug, Clone, Copy, PartialEq, Eq)]
24pub enum AppErrorKind {
25    /// O dado que chegou não passa pelas regras de forma do domínio.
26    ///
27    /// Sempre em lote: quem preencheu o formulário corrige tudo de uma vez.
28    Validation,
29
30    /// Quem está pedindo é conhecido, mas não tem a permissão exigida.
31    Authorization,
32
33    /// Falhou algo que não é do domínio nem do pedido — o banco, a rede, o disco.
34    Internal,
35}
