1//! O contrato entre um VO de resposta e os DTOs que o representam no fio.
2
3use serde::Serialize;
4
5/// Um VO de resposta que sabe virar cada um dos DTOs de saída.
6///
7/// ## Os três objetos, e por que são três
8///
9/// O VO (`…XResponse`) é o **único** que o controller conhece. Ele centraliza os
10/// dados da resposta num tipo independente de formato — nem `Serialize`, nem
11/// tabela do planus, nem nada que amarre a resposta a como ela sai.
12///
13/// Os DTOs são dois, um por formato, e **nenhum dos dois é o outro**: o de
14/// `FlatBuffers` é a tabela que o planus gera do `.fbs`; o de JSON é uma struct
15/// nossa com `#[derive(Serialize)]`. Colar os dois no mesmo tipo — serializar a
16/// tabela do planus como JSON, que era o desenho anterior — amarra o corpo JSON
17/// à forma do `.fbs` e faz uma mudança de schema binário mexer no contrato
18/// textual sem ninguém pedir.
19///
20/// Esta trait é o que amarra os três. Um terceiro formato é um tipo associado a
21/// mais aqui e uma strategy nova — nenhum VO muda, nenhum controller muda.
22///
23/// ## Por que os métodos não falham
24///
25/// Converter um VO num DTO é movimento de dados entre dois tipos que já existem;
26/// não há o que dar errado. O que pode falhar é **serializar** o DTO, e isso é
27/// problema da strategy, que devolve o erro.
28pub(crate) trait ResponseX: Send {
29    /// O DTO de JSON, gerado pelo `derive` do serde.
30    type Json: Serialize;
31
32    /// A tabela do `.fbs`, gerada pelo planus.
33    type Fbs: planus::WriteAsOffset<Self::Fbs>;
34
35    /// O VO na forma que o serde escreve.
36    fn to_json(&self) -> Self::Json;
37
38    /// O VO na forma que o planus escreve.
39    fn to_fbs(&self) -> Self::Fbs;
40}
