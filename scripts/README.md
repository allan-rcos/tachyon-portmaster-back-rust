# `scripts/`

Development and build scripts. All are run from the repository root and resolve
paths from their own location, so they work from anywhere.

| Script | Run it when | Needs |
|---|---|---|
| [`generate-flatbuffers-go.sh`](generate-flatbuffers-go.sh) | a `.fbs` schema changed | `flatc`, `perl`, `gofmt` |
| [`integration-test.sh`](integration-test.sh) | running the Go suite | Docker, Go 1.25 |
| [`build-dist.sh`](build-dist.sh) | building the production artifact | Rust, `musl-tools`, `zstd`, `tar` |

Everything the API itself needs is a `cargo` subcommand and lives in no script:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo doc --workspace --no-deps --open
```

## FlatBuffers

The schemas in `swagger/flatbuffers/schemas/*.fbs` (a submodule) feed both sides
of the contract, by different routes:

| Side | Generated by | When | Committed? |
|---|---|---|---|
| API (Rust) | `planus`, from `crates/api-http/build.rs` | every build | no |
| Tests (Go) | `flatc`, from the script below | by hand | yes |

```bash
scripts/generate-flatbuffers-go.sh    # Go → tests/integration/internal/fbs/
```

**There is no `flatc` on the API side, on purpose.** It would not exist in the
production image, and depending on it would make the build hostage to an
external tool installed apart. `planus` does the same job as a Rust crate, at
build time, and its output never enters the repository — which also means it
cannot go stale.

**`generate-flatbuffers-go.sh`** collapses every schema namespace into one flat
`fbs` package (`--go-namespace fbs`), then strips the cross-file imports and
prefixes flatc leaves dangling when a namespace is overridden. Output *is*
committed, so the test runtime never needs `flatc` — and CI runs this script and
fails on `git diff --exit-code` if the committed bindings are stale. That gate is
what stops the convenience from letting the two sides drift apart.

## Integration tests

```bash
scripts/integration-test.sh                        # everything
scripts/integration-test.sh -run TestYardStory     # one story
INTEGRATION_POOL_SIZE=2 scripts/integration-test.sh
```

Any extra argument is passed through to `go test`. testcontainers-go builds the
API image from the repository `Dockerfile` and stands up its own MariaDB on
tmpfs — `docker-compose.yml` is not involved. Details in
[`tests/integration/README.md`](../tests/integration/README.md).

## Release

```bash
scripts/build-dist.sh              # version from [workspace.package] in Cargo.toml
scripts/build-dist.sh 1.0.0        # or given explicitly
```

Two tarballs land in `dist/`, each with a `.sha256`:

| Artifact | Holds | Applied by |
|---|---|---|
| `portmaster-api-<version>-linux-x86_64.tar.zst` | the static binary | the server |
| `portmaster-migrations-<version>.tar.zst` | `db/migrations` and `db/seeds` | a developer, against the database |

They are separate on purpose. The box running the API is the one least entitled
to change the schema, so the migrations never travel with it — a deployment that
*can* migrate is a deployment that can migrate by accident. See
[ADR 0008](../docs/adr/0008-minified-tarball-as-the-release-artifact.md).

**The binary is static, against musl.** It unpacks onto a bare server with
nothing installed: no runtime, no shared library, no package manager. That is
what keeps a tarball worth having next to the container image — an API process
that *is* the web server has nothing to gain from a container runtime underneath
it. The cost is `musl-tools` on the build machine, for the dependencies that
carry C.

**It is stripped.** Debug symbols are most of the binary and nothing on the
server reads them; the unstripped copy stays in `target/` for whoever has to
resolve a trace, and the `.sha256` says which build it belongs to.

**`--locked`.** The artifact is built from the exact dependency versions that
were tested. A release that silently picked up a new patch version is a release
nobody verified.

Publishing is [`.github/workflows/release.yml`](../.github/workflows/release.yml),
and it hangs off the same field: every push to `main` builds, and the build is
published only when no `v<version>` tag exists yet. Bumping `version` in
`[workspace.package]` is what cuts a release; leaving it alone is what keeps an
existing one untouched. The script itself decides nothing about that — it builds
whatever version it is given, or the one it reads.

## Adding a script

Match the existing shape: a header comment saying what it does and why it exists,
an `Env:` block if it reads any, a `Usage:` line, `set -euo pipefail`, and paths
resolved from `${BASH_SOURCE[0]}` rather than the working directory. Then add a
row to the table above.

LF line endings, always — `.gitattributes` enforces it, and a CRLF shebang is
refused by Alpine with a message that says "no such file or directory" and never
mentions line endings.
